# Spec Delta

## Purpose

Обеспечивает запуск и эксплуатацию системы: строгую конфигурацию, проверки живости, наблюдаемость, безопасные заголовки, хранилище файлов, деплой и резервное копирование.

## ADDED Requirements

### Requirement: Строгая загрузка конфигурации

Система SHALL читать настройки из переменных окружения и SHALL отказываться запускаться без `DATABASE_URL` и `JWT_SECRET`. В production система MUST отклонять короткий `JWT_SECRET`, пароль БД по умолчанию, неполную конфигурацию S3 и backend rate limit, отличный от Redis.

#### Scenario: Отсутствует JWT_SECRET
- **WHEN** приложение запускается без `JWT_SECRET`
- **THEN** старт прерывается с понятной ошибкой конфигурации

#### Scenario: Небезопасный production
- **WHEN** в production задан пароль БД по умолчанию или `JWT_SECRET` короче 32 символов
- **THEN** приложение не стартует

#### Scenario: Production с S3 без параметров
- **WHEN** выбран S3-бэкенд, но не заданы endpoint или bucket
- **THEN** приложение не стартует

### Requirement: Проверки живости и готовности

Система SHALL предоставлять liveness-проверку, не зависящую от БД, и readiness-проверку, подтверждающую соединение с БД. Readiness SHALL возвращать успех только при доступной БД.

#### Scenario: Живая БД
- **WHEN** база данных доступна
- **THEN** readiness отвечает успехом

#### Scenario: БД недоступна
- **WHEN** соединение с БД потеряно
- **THEN** readiness отвечает ошибкой, а liveness продолжает отвечать успехом

### Requirement: Структурированные логи

Система SHALL писать JSON-логи с временем, уровнем, логгером, сообщением, `request_id`, `user_id` (при наличии), маршрутом, методом, статусом и длительностью запроса. Логи MUST NOT содержать пароли, токены и избыточные персональные данные.

#### Scenario: Поиск запроса по идентификатору
- **WHEN** клиент передаёт `X-Request-ID` или получает сгенерированный идентификатор
- **THEN** все записи по запросу содержат этот идентификатор

#### Scenario: Отсутствие секретов
- **WHEN** выполняется вход или обновление токена
- **THEN** в логах нет значений паролей и токенов

### Requirement: Метрики и security headers

Система SHALL отдавать метрики Prometheus по отдельному endpoint при включённом флаге и SHALL добавлять security headers к ответам, включая запрет MIME-sniffing, запрет фрейминга, политику Referrer и Permissions-Policy. HSTS SHALL включаться флагом для работы за HTTPS.

#### Scenario: Метрики включены
- **WHEN** метрики разрешены конфигурацией
- **THEN** endpoint метрик возвращает показатели и не попадает в OpenAPI

#### Scenario: Метрики выключены
- **WHEN** метрики запрещены конфигурацией
- **THEN** endpoint недоступен

#### Scenario: Security headers
- **WHEN** клиент получает любой ответ API
- **THEN** ответ содержит настроенные защитные заголовки

### Requirement: Общий rate limit

Система SHALL поддерживать in-memory и Redis backend для счётчиков rate limit. В production с несколькими процессами MUST использоваться Redis. При недоступности Redis система SHALL логировать сбой и продолжать работу в режиме fail-open.

#### Scenario: Несколько процессов
- **WHEN** production запущен с несколькими worker-процессами
- **THEN** счётчики rate limit общие через Redis

#### Scenario: Redis недоступен
- **WHEN** Redis отвечает ошибкой
- **THEN** запросы не блокируются из-за сбоя счётчика, сбой фиксируется в логах

### Requirement: Хранилище файлов

Система SHALL поддерживать локальное хранилище для разработки и приватное S3-совместимое хранилище для production. Объекты MUST храниться под ключом, не зависящим от исходного имени файла, а доступ SHALL выдаваться только через авторизованный endpoint или короткоживущую подписанную ссылку.

#### Scenario: Локальная разработка
- **WHEN** выбран локальный backend
- **THEN** файлы сохраняются в настроенный каталог медиа

#### Scenario: Production S3
- **WHEN** выбран S3-бэкенд с корректной конфигурацией
- **THEN** файлы сохраняются в приватный bucket, а скачивание проходит через проверку прав

### Requirement: Деплой и миграции

Система SHALL применять миграции отдельным шагом до старта приложения и SHALL запускать backend и фоновый worker как отдельные процессы. Production SHALL публиковать наружу только reverse proxy с TLS.

#### Scenario: Старт production
- **WHEN** стек запускается с нуля
- **THEN** миграции завершаются успешно, затем стартуют backend и worker

#### Scenario: Неудачная миграция
- **WHEN** миграция завершается ошибкой
- **THEN** backend и worker не стартуют

### Requirement: Резервное копирование и восстановление

Система SHALL предоставлять скрипты резервного копирования и восстановления БД и SHALL описывать процедуру проверки восстановления. Секреты MUST храниться вне репозитория.

#### Scenario: Ежедневный бэкап
- **WHEN** запускается скрипт резервного копирования
- **THEN** создаётся дамп БД в настроенном каталоге с учётом срока хранения

#### Scenario: Восстановление
- **WHEN** оператор запускает скрипт восстановления с дампом
- **THEN** данные БД восстанавливаются по описанной в runbook процедуре
