# Design

## Context

См. `proposal.md`. Репозиторий содержит работающий MVP: FastAPI + SQLAlchemy 2.0 async + Alembic + Postgres 16 + Redis/ARQ на backend и Next.js 16 с Cache Components на frontend. Тесты backend (unit/integration) и Playwright E2E зелёные. Задача этого change — описать существующую систему как контракт, поэтому раздел фиксирует уже принятые решения, а не предлагает новые.

## Goals / Non-Goals

**Goals:**

- Единый, проверяемый контракт поведения для каждой capability.
- Прослеживаемая связь между требованиями спецификаций, задачами плана и модулями кода.
- Полный перечень переменных окружения для dev и prod.

**Non-Goals:**

- Новая функциональность, изменение API или схемы БД.
- Внедрение Payload CMS (зафиксирован вариант A — тонкая админка на FastAPI + Next).
- Изменение уже принятых ADR.

## Decisions

- **Baseline, а не изменение поведения.** Delta-спеки используют только `ADDED Requirements`; архивация переносит их в основные `openspec/specs/`. Альтернатива — писать спеки сразу в `openspec/specs/` — отклонена: она обходит валидацию change и теряет историю фиксации.
- **Один репозиторий, два образа.** `backend/` (FastAPI) и `frontend/` (Next.js) собираются и деплоятся раздельно; dev и prod описаны в `deploy/docker-compose*.yml`.
- **Same-origin BFF.** Браузер обращается к `/api/backend/*`, Next проксирует на `/api/v1/*` FastAPI. Cookies остаются first-party, отдельный CORS для браузера не нужен.
- **Сессии в httpOnly cookies.** Access JWT 15 минут, opaque refresh 30 дней с ротацией и отзывом цепочки при повторном использовании; токены никогда не попадают в JSON.
- **Один владелец схемы `public`.** Alembic применяет миграции отдельным one-shot сервисом `migrate` до старта backend и worker. Отдельной схемы CMS нет.
- **Файлы через абстракцию хранилища.** `LocalStorage` в dev, S3-совместимое приватное хранилище в prod; метаданные — в БД, ключ объекта не зависит от имени файла.
- **Напоминания идемпотентны.** ARQ-задача раз в сутки создаёт in-app уведомления с `dedupe_key`; повторный запуск не создаёт дублей.
- **Fail-fast конфигурация.** Отсутствие `DATABASE_URL`/`JWT_SECRET` или небезопасные prod-значения останавливают старт приложения.

## Risks / Trade-offs

- **Расхождение спеки и кода при будущих изменениях** → любое изменение поведения оформляется новым OpenSpec change, а не прямой правкой `openspec/specs/`.
- **Часть критериев плана внешняя** (пилотные участники и даты, реальное восстановление бэкапа, антивирус) → такие пункты остаются неотмеченными с пояснением, а не выдаются за выполненные.
- **Спецификации описывают поведение, а не реализацию** → имена модулей и классов в них не фиксируются, чтобы рефакторинг не требовал изменения спеки.
- **Единая БД для всех сервисов** → риск шумного соседства фоновой нагрузки и API; снижается отдельным worker-процессом и пулом соединений.

## Migration Plan

1. Проверить и зафиксировать delta-спеки, design и tasks.
2. Прогнать `openspec validate core-mvp-baseline --strict`.
3. Архивировать change: `openspec archive core-mvp-baseline` — требования попадут в `openspec/specs/`.
4. Откат не требуется: change не меняет код и данные; при необходимости достаточно удалить каталог change до архивации.
